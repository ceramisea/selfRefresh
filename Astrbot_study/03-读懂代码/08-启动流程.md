# 08 · 启动流程:从 `main.py` 开始发生了什么

> 目标:能说清"敲下启动命令后,AstrBot 按什么顺序把自己组装起来"。
> 对应源码:根 `main.py` → `astrbot/core/initial_loader.py` → `astrbot/core/core_lifecycle.py`。

## 先记住结论

AstrBot 的启动可以概括成一句话:

> **读配置 → 起数据库 → 造一堆"管理器"(平台/模型/插件/定时任务…) → 用事件总线把它们串起来 → 启动各平台适配器去"听消息" → 同时把 WebUI 跑起来。**

它不是"一个程序从头跑到尾",而是**组装一台有很多零件的机器**,零件之间通过"事件"协作。

## 两条启动路径,殊途同归

```
路径 ①  开发/源码方式:  uv run main.py            (根目录 main.py)
路径 ②  安装版/CLI 方式:  astrbot run              (astrbot/cli/commands/cmd_run.py)
                            │
                            ▼
                    都汇合到同一个入口:
                    InitialLoader(...).start()
                    (astrbot/core/initial_loader.py)
```

- 路径①:直接执行 `main.py`,它负责解析参数、准备环境,然后调用 `InitialLoader`.
- 路径②:CLI 的 `run` 命令先做"安全检查"(当前目录必须是有效 AstrBot 目录,即存在 `.astrbot` 标记),设置 `ASTRBOT_ROOT` 环境变量,再调用同样的 `InitialLoader`.

> 这也解释了笔记 02 的一个现象:如果 `cd` 到别的目录执行 `astrbot run`,会报"不是有效的 AstrBot 根目录"。

## 路径① `main.py` 一步步做了什么

打开根目录 `main.py`,按顺序看:

| 行号附近 | 在做什么 | 解释 |
|---|---|---|
| 开头 | `import runtime_bootstrap` | 一个启动引导模块:负责安装缺失依赖、处理运行环境 |
| `_apply_startup_env_flags` | 处理 `--reset-password` 等启动参数 | 在真正 import 核心之前设置环境变量 |
| `check_env()` | 检查 Python 版本,并创建 `data/` 下的目录 | 官方文档要求 Python ≥ 3.12(代码里是宽松的下限检查),先把目录建好避免后面报错 |
| `LogBroker()` + `LogManager.set_queue_handler` | 设置日志系统 | 日志先进队列,再统一展示到控制台/WebUI |
| `asyncio.run(main_async(...))` | **总开关**:启动整个异步程序 | 因为框架是异步的,必须用 `asyncio.run` 包一层 |
| `main_async()` | `await check_dashboard_files(...)` | 确保 WebUI 静态文件可用(没有就尝试下载) |
| `main_async()` | `InitialLoader(db, log_broker).start()` | ★ 真正开始组装框架 |

> 注意 `main.py` 里大量 import 都放在函数外面、文件中部——因为有些模块 import 很慢/依赖环境,`runtime_bootstrap` 要先跑。看到"import 不在文件顶部"别奇怪。

## `InitialLoader` 与核心初始化顺序

`InitialLoader.start()` 内部会转到 `astrbot/core/core_lifecycle.py` 的 `AstrBotCoreLifecycle.initialize()`。下面是**按真实代码顺序**的初始化清单(不用背,看感觉):

| 顺序 | 初始化内容 | 组件 |
|---|---|---|
| 1 | 日志系统 | `core/__init__.py`、`LogManager` |
| 2 | 数据库(SQLite) | `db_helper` / `SQLiteDatabase` |
| 3 | HTML 渲染器(图片渲染用) | `html_renderer` |
| 4 | 配置路由 | `UmopConfigRouter` |
| 5 | **配置管理器(读 cmd_config.json)** | `AstrBotConfigManager` |
| 6 | 数据迁移 | migration |
| 7 | 建事件队列 | `Queue()` |
| 8 | 人格管理器 | `PersonaManager` |
| 9 | 模型提供商管理器(先构造) | `ProviderManager(...)` |
| 10 | 平台管理器(先构造) | `PlatformManager(...)` |
| 11 | 会话/历史管理器 | `ConversationManager` 等 |
| 12 | 知识库管理器 | `KnowledgeBaseManager` |
| 13 | 定时任务管理器 | `CronJobManager` |
| 14 | 子 Agent 编排 | `SubAgentOrchestrator` |
| 15 | 插件上下文(把上面这些都打包) | `Context(...)` |
| 16 | **插件管理器(扫描并加载插件)** | `PluginManager.reload()` |
| 17 | 真正实例化模型提供商 | `provider_manager.initialize()` |
| 18 | 初始化知识库 | `kb_manager.initialize()` |
| 19 | 为每个配置实例建流水线调度器 | `PipelineScheduler` |
| 20 | 建事件总线(队列 → 调度器) | `EventBus` |
| 21 | **启动各平台适配器(开始"听消息")** | `platform_manager.initialize()` |
| 22 | 准备关闭事件 | `asyncio.Event()` |

> 观察要点:**顺序很有讲究**——配置最先(别人都要读配置),平台适配器最后(前面都备好了才开始对外服务),插件在中间(它需要 context,而 context 依赖前面所有管理器)。

## 启动之后:机器开始"转"起来

`initialize()` 把零件造好,`core_lifecycle.start()` 再让它们**转起来**,主要做三件事:

1. 启动**后台任务**:事件总线开始 `dispatch()`(不停从队列取消息事件分发给流水线)、定时任务开始计时、插件注册的周期任务开始跑;
2. 触发系统事件 **`OnAstrBotLoadedEvent`**(框架"我准备好了"),感兴趣的插件可以在这时做初始化;
3. 与 WebUI 后端 **并行运行**(`asyncio.gather`),所以你才能同时访问 `http://localhost:6185`。

到这一步,你的终端会打印"管理面板已启动"和平台适配器的状态——**整个机器人开始在线工作了。**

## 值得打开的三个文件

按顺序点开,配合本笔记看:

1. 根 `main.py` —— 看它怎么把控制权交给框架。
2. `astrbot/core/initial_loader.py` —— 最外层的"启动发起者"。
3. `astrbot/core/core_lifecycle.py` —— 搜 `async def initialize`,感受"所有管理器依次初始化"的节奏。
