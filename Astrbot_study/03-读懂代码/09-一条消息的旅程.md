# 09 · 一条消息的旅程:从"收到消息"到"发出回复"

> 目标:完整讲出"你在 QQ 发一句『你好』,到机器人回复你",中间发生了什么。
> 这是全项目**最核心的一篇**,值得对照代码反复看。
> 对应源码主线:`core/platform/` → `core/event_bus.py` → `core/pipeline/` → `core/provider/`。

## 先建立两个核心概念

**① 事件(Event)= 一封"内部信件"。**
不同平台(QQ/Telegram/… )的消息格式各不相同。AstrBot 不直接处理"QQ 消息"或"TG 消息",而是先把它们**统一翻译成一封信**——`AstrMessageEvent`(`astrbot/core/platform/astr_message_event.py`)。之后整条流水线只认这封信,不关心它来自哪个平台。

**② 流水线(Pipeline)= 一条"处理传送带"。**
这封信会被放进一条流水线,经过一关又一关(Stage)处理。`astrbot/core/pipeline/stage_order.py` 里的 `STAGES_ORDER` 规定了关卡顺序。每关可以"放行"或"拦下"信件,也可以往信上贴便利贴(附加信息)。

## 总览:六站旅程

```
你在 QQ 发:"你好"
   │
   ▼
【站1】平台适配器收到消息  (platform/sources/qqofficial 或 aiocqhttp …)
   │   把平台消息翻译成统一信件 AstrMessageEvent
   ▼
【站2】commit_event 把信投进"总信箱"(event_queue)
   │   EventBus.dispatch() 一直在等信
   ▼
【站3】按消息来源找到对应 PipelineScheduler → 信件上"处理传送带"
   │   按 STAGES_ORDER 一关一关过
   ▼
【站4】WakingCheckStage:这封信要不要理?哪个插件想接?
   │   匹配出 activated_handlers(被"唤醒"的插件处理函数)
   ▼
【站5】ProcessStage 分发:
   │   ├─ 有插件要处理  → StarRequestSubStage(执行插件代码)
   │   └─ 没有插件/该对话 → AgentRequestSubStage → 调大模型(Provider)
   ▼
【站6】回复结果 set_result → RespondStage → event.send() → 平台把消息发回
   │
   ▼
你在 QQ 收到:"你好呀!👋"
```

下面一站一站看。

---

## 站 1:平台适配器收到消息,翻译成"内部信件"

以 OneBot v11(aiocqhttp)适配器为例(其他平台同理):

- 适配器类:`astrbot/core/platform/sources/aiocqhttp/aiocqhttp_platform_adapter.py` 里的 `AiocqhttpAdapter`
- 它启动后一直**监听**消息;收到消息后调用:

```python
self.commit_event(self.create_event(message))
```

拆开看:

- `create_event(message)`:把平台原始消息 `message` **翻译**成一个 `AstrMessageEvent`(统一信件);
- `commit_event(event)`:把这封信投进事件队列。

> `Platform.create_event` / `commit_event` 是适配器基类定义好的方法(`core/platform/platform.py`),子类只需实现"怎么收消息"。

## 站 2:事件总线把信从队列取出来

- 队列在启动时创建(`asyncio.Queue`);`commit_event` 本质是 `queue.put_nowait(event)`。
- `EventBus`(`astrbot/core/event_bus.py`)在后台有个 `dispatch()` 循环,一直 `await queue.get()` **等信**。
- 拿到信后,它根据信上的"来源标识"(`unified_msg_origin`,比如是哪个平台、哪个群),找到**对应那条会话的 `PipelineScheduler`**,调用 `scheduler.execute(event)`。

> 为什么要有 EventBus 这一跳?因为可能有**很多平台、很多群**同时在发消息,队列+分发器让框架能"并发地、不乱套地"处理海量消息。

## 站 3:流水线调度器按顺序跑各 Stage

`PipelineScheduler`(`core/pipeline/scheduler.py`)拿到信后,按 `STAGES_ORDER` 一关一关处理:

```
WakingCheckStage       唤醒检查:要不要理?谁来接?
→ WhitelistCheckStage  白名单
→ SessionStatusCheck   会话状态
→ RateLimitStage       限流
→ ContentSafetyCheck   内容安全
→ PreProcessStage      预处理(STT 语音转文字、图片描述等)
→ ProcessStage         ★ 核心分发:交给插件 or 大模型
→ ResultDecorateStage  结果装饰(加前缀/转图片/TTS)
→ RespondStage         发送回复
```

> 每个 Stage 是一个类;用 `@register_stage` 登记(`core/pipeline/stage.py`)。这种"层层套娃、可插拔"的设计就是**洋葱模型**——中间某关甚至可以"暂停"(yield)等一个异步结果再继续。

## 站 4:WakingCheckStage——"要不要理、谁来接"

`WakingCheckStage` 做两件大事:

1. **判断唤醒**:这条消息是不是在"叫"机器人?(比如私聊、@机器人、以 `/` 开头、命中唤醒词……)
2. **匹配插件**:遍历插件系统里注册的、关心"收到消息"这类事件的所有 handler,用每个 handler 的**过滤器**(`filter`:
   指令前缀、正则、权限、平台类型…)逐一比对,把**命中**的 handler 收集起来,记到信的附加信息里:`activated_handlers`。

相关代码:

- `core/pipeline/waking_check/stage.py`
- `core/star/star_handler.py`(`EventType.AdapterMessageEvent` 就是"收到一条消息"事件类型)
- `core/star/register/star_handler.py`(各种 `@register_*`)
- `core/star/filter/`(各种过滤器)

## 站 5:ProcessStage 分发——两条路二选一

这是"决策点"。`ProcessStage` 看信上的 `activated_handlers`:

**路线 A:有插件要处理**

```python
activated_handlers 不为空
   └─► StarRequestSubStage(core/pipeline/process_stage/method/star_request.py)
          逐个调用插件 handler,执行插件自己写的逻辑
```

比如你发 `/help`,内置"指令插件"的 handler 命中,就返回帮助文本,**不经过大模型**。

**路线 B:没有插件,且应该让 AI 回**

```python
没有插件命中 且 消息是唤醒/指令
   └─► AgentRequestSubStage(core/pipeline/process_stage/method/agent_request.py)
          ├─ 本地 Agent:InternalAgentSubStage
          │    build_main_agent(...) 构造 AgentRunner(ToolLoopAgentRunner)
          │    run_agent(...) 进入"思考→可能调用工具→再思考"循环
          │    最终调用 Provider.text_chat_stream(...) 请求大模型
          └─ 三方 Agent:接入 Dify/Coze 等平台时走这里
```

关键代码位置:

- `core/astr_main_agent.py`(build_main_agent)
- `core/astr_agent_run_util.py`(AgentRunner = ToolLoopAgentRunner)
- `core/provider/provider.py`(`text_chat` / `text_chat_stream` 抽象接口)
- `core/provider/manager.py`(`get_using_provider_async()` 选出当前要用的模型)

> 大白话:站 5 是"先问插件,插件不管再问大模型"。插件像"快捷技能",大模型像"兜底大脑"。

## 站 6:回程——把回复发出去

大模型(或插件)产出的回复被封装成结果对象,放到信上:

- `MessageChain`(`core/message/message_event_result.py`):一串消息组件(Plain 纯文本、Image 图片、At @某人……);
- `event.set_result(MessageEventResult(...))`:把回复"贴"回信上。

然后 `RespondStage`(`core/pipeline/respond/stage.py`)读取结果,调用:

```python
await event.send(chain)
```

`event.send()` 是个"多态"方法——具体怎么发,由**最初那个平台的适配器**决定(因为信记得自己来自哪):

- 来自 QQ,就调到 `aiocqhttp_message_event.py` / `qqofficial_message_event.py` 里的 `send()`,用该平台 SDK 把消息发回 QQ;
- 来自 Telegram,就调到 Telegram 适配器的 send。

> 这就是"平台适配器"设计妙处:中游所有代码只管"信",只有最前(收)和最后(发)两个端点才碰平台细节。

## 顺带认识:系统"事件钩子"

流水线在关键节点会触发"系统事件"(`EventType`),例如:

- `OnLLMRequest` / `OnLLMResponse`:请求大模型前/后
- `OnDecoratingResult`:装饰回复前
- `OnAfterMessageSent`:消息发出后

插件可以用 `@register_on_llm_request()` 之类的装饰器"挂"在这些节点上做横切(比如记录日志、改 prompt)。这是 AstrBot 插件体系的高级玩法,笔记 10 会用到基础的。
