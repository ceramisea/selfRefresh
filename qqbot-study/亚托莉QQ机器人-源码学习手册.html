一套完整的 AI 陪伴机器人工程：基于 OneBot/NapCat 协议接入 QQ， 用 LLM 驱动人设回复，内置分层记忆 + RAG 语义检索、Function Calling 工具系统、 独立语音/歌声服务、桌面宠物与 Web 管理面板。

01

项目全景

在阅读源码前，先建立三个层面的认识：这个项目是什么、 由哪些子系统组成、以及各子系统之间如何协作。

一句话定位

它不是一个「单文件调大模型的脚本」，而是一个多服务系统： NapCat 负责登录 QQ 并转发消息，Python 主服务负责理解与回复， 独立的语音服务负责 TTS/ASR，WebUI 负责运维管理，桌宠负责把这一切包装成 Windows 桌面上的一只小宠物。

02

总体架构

主服务内部按「边界清晰」的原则分层：OneBot 层只管消息生命周期， 回复引擎负责生成文本，消息规划负责把文本拆成可发送的消息，语音/表情只做附加。 下面是关键的数据流与核心边界。

一条消息的完整旅程

NapCat→ server.handle_payload→ 会话队列 + 1.2s 防抖合并→ should_reply 决策
── → 工具分析 ToolAnalyzer→ AtriReplyEngine.reply→ build_outgoing_messages→ send_*_msg
关键决策点都在 server.py 的 _handle_event 中串联；回复引擎只负责「生成最终文本」，不负责协议发送。

核心边界（架构红线）

项目交接文档（docs/PROJECT_HANDOFF.md）用一段话划清了各模块的职责边界，这是理解整个工程的关键：

负责消息生命周期与外部 QQ 交互。不负责编写人设提示词。

唯一的总调度器

负责「当前消息附带材料」的读取与分析。不负责决定最终人设回复。

04

消息接入：OneBot 层

主服务对外只做一件事：监听 NapCat 的反向 WebSocket，收事件、回消息。 所有外部协议细节都被收敛在 onebot/ 包里。

协议角色

NapCat 是一个运行在 Windows 的 QQ 协议桥（Node 程序），登录你的机器人 QQ， 把 QQ 事件转成 OneBot v11 格式，并主动连接主服务的 WebSocket 端口。 主服务不需要了解 QQ 登录细节，也无需拉起 QQ 进程。

反向 WebSocket 的含义
是「NapCat 作为 WS 客户端来连我们」，不是我们去连 NapCat。 所以主服务必须先启动并保持监听；NapCat 断线时主服务不需要重启， NapCat 恢复后会自动重连（配置中 reconnectInterval: 5000）。

关键文件

文件职责
onebot/server.py总调度器：WS 连接、事件分发、会话队列、发送动作（call_action）
onebot/message_parser.py把 OneBot 消息段转成纯文本、提取戳一戳、回复引用
onebot/reply_policy.py是否回复的决策：reply_mode、@检测、群聊触发词
onebot/message_batch.py同一会话短时间内的多条消息合并
runtime/control.pyNapCat 运行状态发布、端口检测、隐藏进程启动

handle_payload：事件分流

收到 WebSocket 帧后按事件类型分三条路：

  • echo/retcode → 是之前某个 action 的异步回包，交给 pending 请求。
  • 戳一戳 notice → 只有「目标是机器人」的才归一化进入对话链路，其他忽略。
  • message → 进会话队列，等待处理。
# onebot/server.py (简化)
async def handle_payload(self, websocket, raw_message):
    event = json.loads(raw_message)
    if "echo" in event and "retcode" in event:
        return self._resolve_pending_action(event)      # action 回包
    if is_poke_event(event):
        event = normalize_poke_event(event, self.config.bot_qq)      # 戳一戳
        if event is None: return
    if event.get("post_type") == "message":
        return self._enqueue_message_event(websocket, event)  # 消息 → 队列
    task = asyncio.create_task(self._handle_event(websocket, event))

会话队列与防抖合并

每个会话（私聊/群聊/群成员）有一个独立 asyncio.Queue 和 worker。 worker 取出第一条消息后等 1.2 秒（MESSAGE_DEBOUNCE_SECONDS）， 把窗口内积压的消息合并成一条，再串行处理。这避免了用户连发多条时机器人并行回复、上下文错乱。

是否回复的决策

should_reply() 按 REPLY_MODE 决定：

模式私聊群聊
private回复不回复
mention回复仅 @机器人 或提到「亚托莉 / atri」
smart回复@/提到 + 一组「亚托莉味」触发词（高性能、哼哒、帮我看看…）
all回复全部回复（不建议大群）

群聊还有一套 GroupReplyFocus（group_reply_focus.py）： 记录最近谁在说话、话题是否延续、以及「图片消息 + 后续 @」的临时绑定（TTL 60 秒）， 让机器人在冷场延续或群友接着追问图片时能接上话。

发送动作 call_action

所有向 QQ 的发送都通过 call_action() 发 OneBot action 到 NapCat：

  • send_private_msg / send_group_msg — 发文本
  • send_msg 带 record 段 — 发语音
  • get_record — 拉取用户语音转为本地文件（配合 ASR）
写在业务里的禁止项
不要把私聊隐私拼进群聊提示词；不要吞异常换固定兜底话术；不要把新功能堆进 server.py 的一个超长分支。

编辑原则：人格文件负责「她是谁、怎么说话」；运行规则负责「什么能做、什么不能声称做过」。涉及工具能力、隐私与安全的规则优先于角色扮演表达。

reply() 的决策顺序

一次回复不是直接丢给 LLM，而是按优先级走一系列「短路」分支：

  1. 好感度命令 — /好感度 之类命令直接本地处理，不经过模型。
  2. 严肃模式 — 用户要求「说人话」等，切回认真模式并短暂压制抽象梗。
  3. 纠错判断 — iteration/judge_correction() 判断是否用户在纠错，记录迭代。
  4. 安慰修复模式 — 检测低落关键词，附加 comfort_repair 提示词。
  5. 视觉失败兜底 — 如果图片分析失败，用明确的失败话术，不假装看见。
  6. 外貌直答 — 「你长什么样」走稳定事实分支，避免模型发挥。
  7. 真正调 LLM — _reply_with_guarded_api() 带完整上下文 + 工具。

上下文如何组装

给模型的消息大致是：

system:  atri_persona.md          # 人格
system:  language_guard.md        # 语言约束
system:  group_chat.md (群聊时)   # 群聊边界
system:  记忆 recall_context      # RAG 召回的「你知道的信息」
system:  工具说明 tool_use.md     # 工具规则
user:    当前消息（+ 图片/文档/语音的分析结果）

记忆以 recall_context() 的稳定接口注入（详见章节 06）， 回复引擎不关心底层是 FTS5 还是向量检索。

回复后的多重「质检 + 修复」

LLM 生成原始回复后，引擎还会做多轮自我审查（human_reply_pipeline_enabled）：

  • 历史 grounding 复核 — 防止把模型自己的旧话当成用户事实。
  • 现实动作复核 — 防止说「我拿起了杯子」「我在看窗外」这类未发生的动作。
  • 语言守卫 — language_guard/detector.py 检测乱码、非法语言、符号垃圾。
  • 人设校验 — lore/ 检查是否越界、是否破坏设定。
  • 迭代修正 — 用户指出「答非所问/重复/套话」后记录并调整后续回复。

核心思想：失败回退是可控的、有边界的——只有模型/工具/合成明确失败才走降级，且错误说明要短，不混入异常堆栈。

06

记忆系统与 RAG 检索

记忆系统让亚托莉「记得」用户：爱好、习惯、好感度、群聊气氛、最近聊了什么。 它是整个项目里最「重」的子系统，也是 v0.3 的重点新增。

两层存储

JSON 事实源

data/memory/users.json 是唯一可编辑的事实源。存用户画像、结构化记忆、好感度、历史、主动互动状态。

memory.py · memory_parts/
SQLite 检索索引

data/memory/semantic_memory.sqlite3 是可删除、可重建的索引。默认 FTS5 全文索引；可选 bge-m3 向量二次召回。

retrieval/repository.py
设计要点
「JSON 存事实、SQLite 只做检索」让两者职责分离：删掉 sqlite 文件不丢任何记忆，重建索引即可。 MEMORY_RETRIEVAL_MAX_CHARS 限制注入上下文的记忆总长度。

三级结构化记忆（L1 / L2 / L3）

层级内容获取方式重要度
L1稳定身份：称呼、兴趣、偏好、习惯LLM 后台提取（memory_extraction）0.95
L2有时间/状态的事件：生日、考试、计划、重要事件LLM 后台提取0.72
L3最近会话原文程序自动保留（deque 最近 80 条）0.45

记忆提取在独立后台线程进行（memory_parts/ingestion.py 的 MemoryExtractionWorker），即使本地模型超时也不影响回复链路。 提取前先由 should_enqueue_memory() 判断这条消息是否值得沉淀 （排除一次性情绪、无意义闲聊、群里转述），避免记忆污染。

从消息到记忆的管道

用户消息→ observe_user()→ MemoryExtractionWorker→ ADD/UPDATE/DELETE 操作→ 写入 L1/L2
LLM 提取遵守 docs/prompts/memory_extraction.md：只提取「新消息中明确或有充分证据」的信息；不提取密码、验证码等敏感信息；群聊只提取群体共同话题。

好感度系统（affection）

每个私聊用户有 0-100 的好感度，owner（主人）初始 72，普通用户 50。它只调节亲近程度，不直接报数值、不覆盖安全规则：

区间状态表现
< 35冷淡回复克制、偏任务型，少撒娇
35 - 50普通自然聊天，偶尔开心/遗憾
50 - 72亲近主动关心、延续旧话题
> 72亲密可表达想念/吃醋，但用安全语言
  • 对话会增减好感：正面/负面事件有每日上限（+1.4 / -1.15），防刷分。
  • 长期不聊会衰减（idle decay），owner 衰减更慢。
  • 好感度还影响主动互动频率和语音请求概率。

召回上下文：recall_context()

# retrieval/planner.py 的 ContextRetrievalPlanner
def build(self, profile, user_text) -> str:
    scope = profile["conversation_id"]
    if self.settings.vector_enabled and has_embeddings:
        vec = await ollama.embed(user_text)          # bge-m3 向量（可选）
        memories = _fuse(fts_results, vector_results)     # 融合两路结果
    lore = repository.search("lore:atri", user_text)     # 仅涉及原作时召回
    return self._render(profile, memories, lore)        # 渲染成模型可读文本
  • 检索前先 _sync_profile() 把 JSON 里的 L1/L2 记忆同步进 SQLite 索引。
  • lore 索引来自 docs/prompts/lore.md 和 atri_persona.md 的分块。
  • 检索是增强项：任何异常都回退到 _format_recall_context() 的纯 profile 渲染，绝不能阻断 QQ 回复。

用户画像的动态适配

observe_user() 会统计消息长度、回复间隔、表情频率、提问频率、话题词、纠错次数等， 生成「对话习惯画像」（如偏好长回复还是短回复、爱不爱用 emoji）， 由回复引擎通过 preferred_parts 等字段动态调整拆分条数和表情概率。

工具是否暴露由配置决定：available_tool_schemas(config) 根据 web_search_enabled、voice_tts_enabled 等开关组合。

工具调用循环 tool_loop

# 一次工具调用的消息流
messages += [assistant(tool_calls=[...])]     # 模型请求调用
for call in tool_calls[:max_calls]:          # llm_tool_max_calls=2
    content = await executor(name, args)    # 执行工具
    messages += [tool(tool_call_id, content)]  # 结果回填
# 再调一次 LLM，让模型基于工具结果给出最终回复
  • 参数解析失败或执行失败时，注入「不要编造工具结果」的明确错误，而不是静默吞掉。
  • 每次工具调用写入 logs/llm-tools.jsonl，便于排障。
  • _tool_result_failed() 识别失败前缀（工具执行失败 / 未启用 / 搜索失败…）。

网络工具的可靠性设计

搜索 grounding

搜索结果区分「搜索到」与「能够支持当前结论」：_append_primary_source_excerpt() 附加首条原文片段，并做相关性检查。无关结果不能作为证据。

web_search_tool.py
网页读取防 SSRF

open_web_page 校验 URL 必须是公网主机名，拒绝内网/保留 IP，防止读取本地敏感服务；提取正文有字节上限（1.5MB）和字符上限（8000）。

web_page_tool.py

Material Toolbox：消息附带的材料

与「模型自主调工具」并列的是 toolbox.py：用户在 QQ 里发的图片、文档、表格、视频、网页链接。 它不靠模型决策，而是在每次回复前由 ToolAnalyzer.analyze() 主动解析：

材料处理方式
文本文件 (.txt/.md/.csv)抽取正文，截断到 MAX_TEXT_CHARS
文档 (.docx/.pdf)pypdf 抽取文本、docx 解 zip 抽 XML 文本
表格 (.xlsx)读取 sheet 行，数值列做概览（均值/分布）
图片OCR（rapidocr）+ 本地视觉模型（qwen3-vl）识图与审美
视频ffmpeg 抽关键帧（最多 4 帧）+ 视觉模型分析
网页/B站HTML 提取正文 / B站 API 拉标题字幕
视觉链路硬约束
当前图片优先于旧图片；没有图片时不得声称「看到了」；视觉模型无法确认身份时必须说「未确认」； 聊天模型和视觉模型共用 Ollama 且显存不足时串行加载，不能并发硬挤显存。

Agent 协议（可选）

开启 LLM_AGENT_PROTOCOL_ENABLED 后启用多步协商：模型可以在多轮内决定动作，最终用 final_answer 收尾。默认关闭，普通单轮工具循环已足够。

消息规划与表情

回复文本生成后，进入发送前的「规划」阶段：拆成多条短消息模拟流式、按情绪附一张表情。 这一层不重新生成内容，只做转换。

OutgoingMessage

规划产物是统一的中间对象：

# message_plan/schema.py
@dataclass(frozen=True)
class OutgoingMessage:
    kind: Literal["text", "image", "face", "record"]   # 文本/图片/QQ表情/语音
    content: str                                    # 文本内容 or 文件 URL or face id

outgoing_to_onebot_message() 负责把 OutgoingMessage 转成 OneBot 消息段数组。

文本拆分

split_reply_text() 把长回复按句子/逗号/空格切成不超过 MESSAGE_SPLIT_MAX_CHARS（默认 44 字符）的片段，最多 MESSAGE_SPLIT_MAX_PARTS（默认 4）条。每条之间还有随机延迟（0.55-1.35s）模拟打字节奏。

# 效果：长回复被拆成多条短消息，避免刷屏
回复1: 哼，高性能亚托莉上线啦。
回复2: 你刚才说的那个项目我记着呢。
回复3: 要不要先试试搜索最新资料？ [表情]

发送之间会参考用户画像的 preferred_parts（历史偏好条数）动态调整。

表情系统

sticker_parts/core.py 定义了情绪分类与发送优先级：

发送优先级：
  手动添加本地表情 > 聊天记录归档表情 > 默认联网缓存 > 网页 URL > QQ 自带表情 + emoji
  • 目录结构：data/stickers/<emotion>/，情绪包括 happy/comfort/tired/proud/confused/shy/food/goodnight 等。
  • StickerManager.choose() 根据用户文本 + 回复文本检测情绪，按概率（STICKER_CHANCE）选择表情，带冷却时间。
  • 自定义触发词：data/stickers/triggers.json，如「高性能 → proud」。
  • 自动捕获：聊天记录里的图片会归档到 data/stickers/_chat_history，之后可复用。

OneBot 发送适配

发送时 call_action() 会根据消息类型调用 send_private_msg / send_group_msg， 语音则发送 record 段（本地文件走 base64）。发送结果会记录到 logs/reply-events.jsonl。

主动互动

不只是「被动回复」，亚托莉还会主动找人：早安、空闲关心、群聊冷场插话。 这套逻辑在 proactive/ 包和 memory.py 的定时器里。

三类主动行为

行为默认触发条件
早安问候开启 · 07:30每天早上一次；只发给 OWNER_QQ 或私聊过的人

主动规划 v2（可选）

PROACTIVE_V2_ENABLED 开启后使用 proactive/planner.py： 按好感度分层（冷淡/普通/亲近/亲密），每层有不同的打扰频率、安静时段、事件类型 （morning/goodnight/check_in/continue_topic/interest_topic/guided_topic/daily_share/affection/encouragement）。 计划写入记忆，由定时器检查是否到期。默认关闭，使用旧版 idle/morning 循环。

{
  "tier": "close",            # 亲密度分层
  "event_type": "continue_topic", # 事件类型

防骚扰机制

  • 所有主动消息都有冷却时间与每日上限。
  • 安静时段不打扰（由 proactive/policy.py 的 quiet_hours 控制）。
  • 用户连续忽略会降低打扰频率（ignored_streak 累加）。
  • 群聊主动消息必须「多人可参与、不点名个人、不使用私聊记忆」。

语音与歌声

语音是附加链路，不是文本的替代。文本已经生成后，语音策略再决定是否附加。 默认关闭，失败自动回退文字，不影响聊天。

两个进程的分工

进程目录职责
QQ 主进程src/atri_qq_bot/voice/语音决策：是否发语音、请求 TTS、发送 record
语音服务src/atri_voice_service/语音执行：ASR、TTS 合成、原声匹配、歌声任务

两者通过 HTTP（默认 http://127.0.0.1:8790）通信。

语音决策链（QQ 主进程侧）

用户语音 → ASR 转文本→ 模型可自主调用 speak_as_atri→ 显式请求保护器→ voice_policy 评估→ 合成 → 质量门 → 发送
「用语音回复我」「读出来」「唱两句」会被显式请求保护器（explicit_delivery_intent）补建语音请求，即使模型漏调工具。

voice/manager.py 的 VoiceManager 负责调度， voice/policy.py 的 evaluate_voice_request() 根据 明确要求、情绪、概率、好感度、群聊开关、冷却时间决定是否放行。

语音服务内部（atri_voice_service）

SpeechApplication
├─ ConversationSpeechPipeline     # mode=speech 日常语音
│  ├─ 完整原声匹配 (original_library.py)
│  ├─ GPT-SoVITS 合成 (providers.py)
│  └─ ASR 回读检查 → 重试 → 中性补救 → 拒发
└─ SingingService                 # mode=singing 歌声任务
   └─ SingingJobManager           # 人声分离 + SVC + 混音 + 质量检查
  • ASR：SenseVoice + FSMN-VAD 分段，支持热词（asr-hotwords.json）与口音矫正。
  • TTS：GPT-SoVITS 主引擎；优先匹配官方原声素材（ATRI训练音频素材 目录），相似度 ≥0.94 才直接发原声。
  • 质量门：合成后用 SenseVoice 回读，计算汉字 + 带声调拼音错误率；超阈值用不同 seed 重试；全部失败切中文救援档案；仍失败则拒发并回退文字。
  • 流式语音：长文本按语义段（默认 34 发音单位）切分，每段合成完立即发送，支持说话中被打断。

歌声合成

歌声走异步任务：POST /v1/singing/jobs 提交 → SingingJobManager 排队 → 人声分离 → 乐理分段 → SVC 转换 → 混音 → 质量检查 → 导出。任务进度可查询、可取消。 生成式唱歌依赖外部工具链（种子声源 + 训练管线），未配置时不影响普通 TTS。

关键配置

VOICE_ASR_ENABLED=false        # 语音输入（默认关）
VOICE_TTS_ENABLED=false        # 语音输出（默认关）
VOICE_SERVICE_URL=http://127.0.0.1:8790
VOICE_PROFILE=atri-official-v2pro-curated
VOICE_SEGMENT_MAX_CHARS=34     # 语音切段粒度

热加载机制

WebUI 修改配置后调用 WebUIState.reload_config()， 运行中的服务据此重建轻量对象（如检索 Planner、VoiceManager 配置），不需要重启。 修改 .env 与 data/webui/*.json 都会持久化。

边界
WebUI 只改配置和数据文件；不能直接改内存对象。重启后配置必须仍然存在。

本地模型扫描的「发现 ≠ 可用」

/api/local-models 扫描本地 Ollama 模型目录，但文件存在不等于 Ollama 已注册可运行。 UI 明确区分「发现文件」与「实际可调用」，启用前会验证 provider / base URL / 模型名 / 本地实际运行状态。

二次开发指南

想改代码？先理解项目的「开发纪律」——它决定哪些改动是安全的、哪些会破坏架构。

新功能接入流程

项目交接文档规定，开发必须先按顺序回答：

  1. 先描述现有链路：入口、配置、运行时对象、持久化、发送出口、失败出口。
  2. 明确新功能属于哪个边界：OneBot / 工具 / 回复 / 人设 / 记忆 / 语音 / WebUI / 独立服务。
  3. 先加配置 schema → loader → WebUI 展示与持久化 → 再接运行时；配置要有默认值和关闭开关。
  4. 新模型先做独立健康检查与最小调用，不直接替换生产模型。
  5. 写单元测试（成功/超时/空结果/错误响应/模型切换/重启持久化）。
  6. 端到端测试并保存可观测日志。

配置新增三步

# 1. schema.py 加字段（含默认值）
class BotConfig:
    my_new_flag: bool = False

# 2. loader.py 从 .env 读取并校验
my_new_flag = _env_bool("MY_NEW_FLAG", False)

# 3. 需要时在 webui/config_admin.py 暴露

添加一个新 LLM 工具

  1. 在 llm_tools/ 新建 xxx_tool.py，实现处理函数。
  2. 在 schema.py 写工具 JSON Schema，并加入 available_tool_schemas()。
  3. 在 registry.py 注册 handler。
  4. 在 docs/prompts/tool_use.md 补充工具使用规则。
  5. 写测试（tests/test_llm_tools.py）。

开发禁止事项（红线）

  • 不要把新功能塞进 server.py 的超长分支（除非只是外部事件编排）。
